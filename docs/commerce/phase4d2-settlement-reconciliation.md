## Status

**In progress — the import/reconciliation foundation and cross-currency classification are merged; PR #38 adds private evidence custody and PR #39 adds adversarial import/reconciliation tests. ## Research basis

The contract is intentionally normalized rather than provider-report-specific. Adyen's official settlement-details documentation describes transaction-level settlement records and distinct transaction, fee, correction, and payout entries. Its fee-reconciliation guidance warns that report periods and time zones must align. These facts inform the explicit report period, timezone, row type, references, amounts, and exception fields here:

- [Adyen — Settlement details report](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/)
- [Adyen — Reconcile fees](https://docs.adyen.com/classic-platforms/reconciliation-use-cases/understand-fees)

This is design research, not evidence that Web-Temify has selected, onboarded, or integrated Adyen or any other provider.

The merged foundation adds immutable reconciliation runs/results, distinct-admin review, idempotent retries, and exception triage that cannot mutate reconciliation evidence. PR #31 merged migration `20261014010000_phase4d2_currency_mismatch_classification.sql`, checking provider-reference uniqueness before currency filtering, with pgTAP fixtures for a real posted sandbox payment journal, exact matched-payment linkage, and cross-currency mismatch classification. - Rows have stable identifiers, an explicit row type, optional provider/internal payment references, an offset-aware timestamp, currency, gross/fee/net minor-unit values, and a bounded exception taxonomy.
- Validation rejects unknown keys, duplicate row IDs within a report, currency mismatch, rows outside the declared period, inverted periods, invalid source digests, positive-gross refunds, non-positive-gross payments, and positive-net fee rows.
- Contract tests cover accepted report payloads and the listed schema-validation boundaries. They do not establish complete reconciliation correctness; the missing reconciliation adversarial cases are tracked explicitly below.
- Forward migration `20261014030000_phase4d2_preserve_import_exception_codes.sql` preserves explicit imported `period_mismatch` and `unexplained_adjustment` classifications before journal matching, expands the reconciliation result constraint, and retains the previously merged cross-currency mismatch behavior. pgTAP regression cases verify that explicitly classified exception rows cannot be promoted to matched payments. This is a code-level classification fix only; it does not authenticate source files, store evidence objects, post settlement/fee journals, or resolve exceptions.
- The merged admin exception queue is backed by a bounded service-only RPC. The RPC rechecks the database-owned admin role, limits page size and cursor shape, exposes normalized row/report fields and immutable triage metadata, and cannot resolve exceptions or post journals. A same-origin, bounded decision endpoint requires independent-admin approval in the database, validates evidence-digest rules, and records the requested action in the audit stream before mutation. Triage decisions are immutable and do not resolve accounting exceptions. Pagination uses an exclusive `(created_at, run_id, row_id)` cursor with bounded row identifiers, and minor-unit amounts are returned as decimal text to avoid JavaScript integer precision loss.

The forward migration `20261014070000_phase4d2_global_journal_match_guard.sql` replaces the per-run-only uniqueness rule with a global unique partial index on `journal_batch_id`. A single posted financial journal batch therefore cannot be counted as matched by two different settlement imports. The migration fails closed if historical reconciliation evidence already contains duplicate batch matches, requiring forensic review rather than rewriting immutable evidence. A schema-level pgTAP assertion verifies the unique partial index.

The follow-up migrations `20261014080000_phase4d2_classify_duplicate_journal_matches.sql` and `20261014090000_phase4d2_preserve_currency_and_replay_guards.sql` classify cross-import replays as immutable `duplicate_reference` exceptions instead of aborting the reconciliation transaction. Candidate journal batches are locked in deterministic UUID order using transaction-scoped advisory locks to reduce concurrent double-match and deadlock risk; the global unique index remains the final integrity backstop. Dedicated concurrent-race tests, matched-refund correctness, provider-authenticated ingress, settlement/fee posting, retention, malware scanning, escalation/expiry, and external onboarding remain open. ## Critical trust boundary

sourceAuthenticated=true is a trusted-ingress assertion, **not cryptographic verification**. A future server-side import route must authenticate the operator, authenticate the source file or API response, calculate the digest from the exact bytes received, enforce byte/row limits, persist immutable import evidence, and record who/what verified it. Clients must never be allowed to set this assertion and then trigger posting.

Contract validation does not prove that netMinor = grossMinor - feeMinor: settlement semantics vary by row type and provider. It does not perform FX conversion. Version 1 requires one currency per report and per row; multi-currency reports must be split or rejected until an explicit FX-aware contract is reviewed. Values are integer minor units, never floating-point decimal amounts.

## Required next work before Phase 4D2 can pass

1. Authenticate the actual source at trusted ingress. The admin-only evidence endpoint calculates SHA-256 from exact received bytes and supports private storage/retrieval, but an authenticated admin upload is not provider authentication. Add provider-specific signed API/report verification, bind verified source identity and account to the import, validate timezone/report metadata, and never accept the database boolean as cryptographic proof.
2. Extend the initial payment/refund match snapshot with complete verified-journal linkage and adversarial fixtures for matched payments/refunds, duplicate references, cross-currency and amount mismatches, timezone edges, fee-only rows, and unexplained adjustments. Current reconciliation records missing matches, duplicate references, amount mismatches, currency mismatches and unsupported row types; matched-payment and cross-currency fixtures now exist, but refund matches and broader adversarial cases remain untested. A separate triage decision can require reimport, request manual review, or record an evidence digest for independent review; it does not resolve the accounting exception, change the reconciliation result, or authorize journal posting. Never auto-resolve an exception.
3. Implement source-specific posting guards for provider settlement and provider fees. Require balanced same-currency entries, evidence linkage, row-level reconciliation, and idempotency; keep money movement and payout execution disabled.
4. Extend pgTAP and application tests for concurrent duplicate imports/reconciliation, matched refunds, journal imbalance, and retry behavior. Duplicate cross-import journal references are now classified and covered by the existing reconciliation suite; true concurrent-race coverage remains open. PR #39 adds tests for unmatched refunds, fee-only rows, explicit adjustment exceptions, unknown timezones, local-date/UTC boundaries, out-of-period rows, and atomic rollback when a later import row is invalid. Existing tests cover identical import replay, exact matched-payment linkage, duplicate settlement rows targeting one journal batch, amount mismatches, cross-currency mismatch, and explicit exception preservation. Provider-authenticated source ingress and concurrent retry behavior still require dedicated tests.
5. The bounded admin exception workflow provides read-only visibility and immutable triage decisions with pre-mutation audit and database-enforced independent-admin checks. PR #38 adds admin-only private evidence upload/download; this branch adds a service-only link RPC and admin endpoint that bind the evidence digest to the import digest and require a reviewer distinct from both uploader and importer. The link and its completion audit event commit atomically. This is evidence custody and linkage, not provider authentication. Automated retention enforcement/deletion, malware scanning, provider-authenticated ingress, escalation/expiry policy, second approval where required, and full audit/retention review remain open. Triage does not resolve/post exceptions.
6. Run empty-database migration reset, schema lint, full database/RLS tests, foundation/domain tests, typecheck, lint, format, Playwright, production build, security/dependency/license/secret scans, and an exact-head forensic review.
7. Record provider selection, supported jurisdictions/currencies, fees, dispute/refund behavior, settlement report semantics, and onboarding evidence separately. Until those are verified, all live-provider processing remains disabled.
