# Phase 4D2 — provider-neutral settlement import contract

## Status

**In progress — the import/reconciliation foundation, cross-currency classification, private evidence custody, and evidence-to-import linkage are merged. The follow-up `20261014130000_phase4d2_sandbox_fee_journal_posting.sql` adds a sandbox-only provider-fee journal path behind linked-evidence and independent-review gates.** Live-provider ingress, provider settlement/payout posting, automated retention enforcement, production scanner deployment/configuration, scanner-signature freshness monitoring, escalation/expiry policy, complete concurrency coverage, and external provider evidence remain incomplete. A fail-closed database gate requires an immutable, digest-matched clean scan attestation before evidence linkage or fee posting. A separate ClamAV gateway and upload-route client now implement scanning in code, but no production endpoint or credentials have been configured or verified. The admin exception queue supports immutable triage decisions, but a triage decision does not resolve an accounting exception or authorize posting. Do not enable live-provider processing or claim Phase 4D2 complete.

## Research basis

The contract is intentionally normalized rather than provider-report-specific. Adyen's official settlement-details documentation describes transaction-level settlement records and distinct transaction, fee, correction, and payout entries. Its fee-reconciliation guidance warns that report periods and time zones must align. These facts inform the explicit report period, timezone, row type, references, amounts, and exception fields here:

- [Adyen — Settlement details report](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/)
- [Adyen — Reconcile fees](https://docs.adyen.com/classic-platforms/reconciliation-use-cases/understand-fees)

This is design research, not evidence that Web-Temify has selected, onboarded, or integrated Adyen or any other provider.

## Sandbox-only provider-fee journal posting (partial implementation)

Migration `20261014130000_phase4d2_sandbox_fee_journal_posting.sql` adds a narrowly scoped provider-fee journal path to the independent reconciliation workflow.

- Only `provider='sandbox'` imports authenticated as `sandbox_fixture` can use this path. Non-sandbox imports remain rejected at trusted ingress.
- Fee rows must have `gross_minor = 0`, `fee_minor > 0`, and `net_minor = -fee_minor`. Invalid arithmetic fails before a report can be reconciled.
- The report's private evidence digest must be linked to the import by an independent admin before fee posting. The reconciliation reviewer must be an admin distinct from the importer, evidence uploader, and evidence linker.
- The posting creates exactly two same-currency entries: debit `provider_fee_expense` and credit `provider_clearing`, each for the exact fee amount. A source-specific journal guard verifies the normalized row, linked evidence digest, immutable posting link, independent reviewer, source key, and balanced entries before the batch can become posted.
- A unique import-row posting link, stable source/idempotency key, per-row advisory lock, immutable result row, and correlated audit event provide atomicity and replay protection.
- A missing evidence link or invalid reviewer aborts the transaction without leaving a reconciliation run or journal batch. Evidence can be linked and the reconciliation retried.
- This is not provider settlement/payout posting, live provider integration, or money movement. Payout, settlement cash movement, and all non-sandbox provider paths remain disabled.

The dedicated pgTAP suite `supabase/tests/phase4d2_sandbox_fee_posting.test.sql` covers balanced posting, digest linkage, independent actors, immutable posting evidence, replay idempotency, missing-evidence rollback/retry, and invalid fee arithmetic. Migration `20261014140000_phase4d2_evidence_malware_gate.sql` adds immutable scanner attestations and requires the latest digest-matched verdict to be clean before evidence linkage or fee posting. The service-role-only RPC is an attestation boundary, not a scanner; a trusted scanner integration must inspect the exact stored bytes and report the verdict. The Phase 4D2 gate remains open for scanner integration, concurrent-race testing, provider-authenticated ingress, settlement/payout posting, retention/deletion enforcement, escalation/expiry, and external onboarding evidence.

## Malware-scan gate (partial implementation)

Migration `20261014140000_phase4d2_evidence_malware_gate.sql` adds append-only `settlement_evidence_scan_results` records with the evidence digest, verdict, scanner name/version, server timestamp, and correlated audit event.

- Only the service-role scanner attestation RPC can add results; browser/authenticated roles cannot insert or read scan attestations.
- The RPC requires the exact SHA-256 already recorded for the private evidence object. A digest mismatch fails without an attestation.
- Evidence linkage fails closed when no scan exists or the latest verdict is `infected` or `error`. A subsequent clean rescan restores eligibility without mutating prior scan history.
- The financial journal guard independently checks the latest scan verdict and digest at posting time, so a scan marked infected after linkage cannot be used to post a provider-fee journal.
- Scan attestations and their audit events are append-only and committed atomically.
- **Runtime gate:** the repository now includes `services/settlement-scanner/`, a token-protected ClamAV gateway that scans the exact bytes with INSTREAM, independently computes SHA-256, and returns clean/infected/error. The admin upload route invokes it when `CLAMAV_SCANNER_URL` and `CLAMAV_SCANNER_TOKEN` are configured, then records the verdict through the service-only RPC. When configuration is absent, the scanner is unreachable, or the response fails digest validation, the evidence remains pending and cannot be linked or posted. Production deployment, HTTPS ingress, secret configuration, signature-freshness monitoring, and a live scanner smoke test are still required.

The dedicated `supabase/tests/phase4d2_evidence_malware_gate.test.sql` covers least privilege, pending/infected denial, digest mismatch, clean scanning, immutable history, audit events, and clean-rescan recovery.

## Critical trust boundary

sourceAuthenticated=true is a trusted-ingress assertion, **not cryptographic verification**. A future server-side import route must authenticate the operator, authenticate the source file or API response, calculate the digest from the exact bytes received, enforce byte/row limits, persist immutable import evidence, and record who/what verified it. Clients must never be allowed to set this assertion and then trigger posting.

Contract validation does not prove that netMinor = grossMinor - feeMinor: settlement semantics vary by row type and provider. It does not perform FX conversion. Version 1 requires one currency per report and per row; multi-currency reports must be split or rejected until an explicit FX-aware contract is reviewed. Values are integer minor units, never floating-point decimal amounts.
